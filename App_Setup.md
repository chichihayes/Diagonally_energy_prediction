## Where Skills Are Discovered

Both Claude Code and Codex CLI auto-discover skills from `.claude/skills/`.
A skill is a folder containing a `SKILL.md` file — the folder name becomes
the slash command. Frontmatter has only two fields:

```markdown
---
name: grill-me
description: Interview the user about a feature until alignment is reached.
---

# Skill: Grill Me

[Instructions for the AI]
```

The `description` is what the AI reads to decide whether the skill is relevant.
Make it specific so triggering accuracy is high.

**For Codex compatibility:** setup.sh creates a symlink at `.codex/skills`
pointing to `../.claude/skills` so Codex finds the same skills without duplication.
On Mac and Linux this works out of the box. On Windows, replace the symlink
with a junction (`mklink /D`) or duplicate the files.

## Where Spec Documents Fit in the Workflow

The `docs/` folder is a persistent layer that runs underneath all phases.
It answers a different question than the PRD:

| Document | Answers |
|---|---|
| PRD | What are we building this sprint and why? |
| `docs/schema.md` | How is the database structured right now? |
| `docs/api-contracts.md` | What is the exact shape of every API route? |
| `docs/auth.md` | How does authentication and authorisation work? |
| `docs/architecture.md` | How is the system organised? |
| `docs/decisions.md` | Why was the system built this way? |
| `docs/env.md` | What environment variables are needed? |

Spec docs are generated once (by `/write-specs` from the PRD), reviewed and
edited by you, then treated as read-only source of truth. The agent reads them
only when an issue references them. It never modifies them unless explicitly
instructed by the issue.

## File Specifications

### CLAUDE.md

Loaded automatically by Claude Code at the start of every session. Under 2,000 tokens. Contains all coding standards the agent applies to every task — no per-task instructions here.

**Sections:**
- Stack
- Spec Documents (docs/ reference)
- Architecture + Module Map
- Naming Conventions
- Error Handling
- Security Standards
- API Design
- Performance
- Supabase Conventions
- TDD Rules
- Coding Standards
- Communication Style
- Test Integrity

---

### AGENTS.md

Read by Codex and other agents. Mirrors CLAUDE.md standards in Codex-compatible framing. Includes the full 10-step task sequence, self-audit checklist, and TDD protocol.

---

### docs/ Spec Documents

**When created:** After PRD is confirmed, before epics are created. Use `/write-specs`.

**Who writes them:** Claude drafts from the PRD. You review, fill placeholders, and lock them.

**How the agent uses them:** The agent reads only the docs listed under `## Reference Docs` in the specific issue file. It does not scan the whole docs/ folder.

**Update policy:** Spec docs are read-only during implementation. If an issue requires a spec doc update (e.g. a new table or route), the issue file must explicitly state which doc to update and how.

**Doc rot prevention:** After a feature ships and the spec has changed, update docs/ manually. Old specs mislead future agents more than missing specs do.

---

### issues/ Directory

Full hierarchy: PRD → Epics → Features → Issues.

| Path | Level | Purpose |
|---|---|---|
| `issues/prd-[name].md` | L2 | Destination doc, one per idea |
| `issues/epics/E[N]-[slug].md` | L3 | One per epic |
| `issues/features/[epic]/F[N]-[slug].md` | L4 | One per feature |
| `issues/open/[NNN]-[slug].md` | L5 | Agent work orders |
| `issues/done/` | — | Merged issues |
| `issues/discovered/` | — | Agent-found bugs |

**Issue file template** (generated by `/feature-to-issues`):

```markdown
# Issue [NNN]: [Title]

**Epic:** E[N]-[slug]
**Feature:** F[N]-[slug]
**Type:** AFK | Human-in-loop
**Status:** open
**Blocked by:** #[NNN] | nothing
**Priority:** critical | high | normal | low
**Branch:** feature/[NNN]-[slug]

## Goal
One sentence: what does done look like from a user's perspective?

## User Story
As a [user type], I want [action] so that [outcome].

## Reference Docs
- `docs/schema.md` — [which tables/columns apply]
- `docs/api-contracts.md` — [which routes apply]
- `docs/auth.md` — [if auth is involved]

## Acceptance Criteria
- [ ] [mirrors Test 1 outcome]
- [ ] [mirrors Test 2 outcome]

## Files to Modify
- `src/services/[name].service.ts` — [what changes]
- `supabase/migrations/[ts]_[name].sql` — [new table/column]
- `src/app/api/[route]/route.ts` — [what changes]
- `src/components/[Name].tsx` — [what the user sees]

## Out of Scope
- [explicitly not in this issue]

## Implementation Plan

Step 1: [what to build]
Test 1: [exact assertion the test will make]
File:   [test file + implementation file]

Step 2: [what to build]
Test 2: [exact assertion]
File:   [files]

## Git
- Branch: `feature/[NNN]-[slug]`
- Commit: `feat([scope]): [description] closes #[NNN]`
- PR title: `[NNN] [Title]`

## Implementation Notes
[Decisions from Grill Me or ADRs that affect this]
```

### skills/write-specs.md

**When to use:** Immediately after the PRD is confirmed. Before running `/prd-to-epics`.

**How to invoke:**
```bash
/write-specs issues/prd-[name].md
```

Generates all six docs/ files from PRD content. Marks unknowns as `<!-- TODO -->` placeholders. You review, fill placeholders, and lock the files before proceeding to epics.

---

### skills/feature-to-issues.md

**When to use:** Once per feature, after epic-to-features completes.

**How to invoke:**
```bash
/feature-to-issues issues/features/[epic]/F[N]-[slug].md
```

Produces fully-specified issue files including: Reference Docs, detailed Implementation Plan with per-step TDD tests, and exact Files to Modify paths.

---

### skills/implement.md

The AFK loop prompt. Passes to every agent run via `once.sh` and `ralph.sh`. Instructs the agent to:

1. Load Epic + Feature files for orientation
2. Read referenced spec docs
3. Create the feature branch
4. Execute the Implementation Plan step by step (strict TDD)
5. Run the full feedback loop
6. Run the self-audit checklist
7. Commit and push

---

### skills/audit.md

**When to use:** After each AFK loop, in a fresh context, before opening a PR for human review.

**How to invoke:**
```bash
git diff main...feature/NNN-slug | claude "$(cat skills/audit.md)" \
  (the audit prompt embeds ISSUE and SPEC_DOCS directly via stdin —
  see BUILD_GUIDE.md for the full pattern)
```

Checks seven dimensions: TDD Integrity, Spec Compliance, Security, Error Handling, Performance, Coding Standards, Scope Discipline. Outputs a structured PASS/FAIL report. The PR is only opened after the audit returns `[APPROVED]`.

### scripts/once.sh and scripts/ralph.sh

Both scripts now pass four context blocks to every agent run:
- `RECENT COMMITS` — last 5 commits for continuity
- `EPICS` — all epic files for orientation
- `FEATURES` — all feature files for sibling context
- `ISSUES` — all open issue files

## Step 3 — Full Workflow (Idea to Merged PR)

```
Phase 1 — Alignment (human-in-the-loop)
  /grill-me → describe the idea or paste clientbrief.md
  Answer until aligned → type: write the PRD

Phase 2 — Destination doc (human review)
  Review: module map, out of scope, acceptance criteria → confirm

Phase 2b — Spec docs (human review)
  /write-specs issues/prd-[name].md
  Review docs/ → fill all <!-- TODO --> placeholders → lock

Phase 3 — Planning (human review at each step)
  /prd-to-epics issues/prd-[name].md
  Review epics → confirm
  /epic-to-features issues/epics/E[N]-[slug].md  (per epic)
  Review features → confirm
  /feature-to-issues issues/features/[epic]/F[N]-[slug].md  (per feature)
  Review issues + implementation plans → confirm → files written to issues/open/

Phase 3d — Issue Planning (human review)
  /plan-issues              ← generates EXECUTION_PLAN.md + worktree-run.sh
  Review DAG diagram and phase assignments
  Confirm no missing dependencies

Phase 4 — Implementation (worktrees, per phase)
  ./scripts/once.sh                  ← verify one issue runs cleanly first
  ./scripts/worktree-run.sh 1        ← run Phase 1 in parallel worktrees
  ./scripts/status.sh                ← check progress at any time
  Open PRs on GitHub for APPROVED branches
  Review + merge PRs (Squash and merge)
  ./scripts/worktree-merge.sh 1      ← cleanup Phase 1
  (repeat worktree-run / merge for each phase)

Phase 5 — Audit + Review (human)
  git diff main...feature/NNN | claude "$(cat skills/audit.md)" ...
  Review audit report → agent fixes FAIL items → re-audit
  Open PR → human reviews → merge → move issue to issues/done/
  Create new issues from QA findings
```

## Keeping the Workflow Healthy

- **Spec docs are source of truth.** If the implementation drifts from docs/, update docs/ not the implementation.
- **Audit before every PR.** The agent self-audits, but the external audit skill catches what the agent misses.
- **Check status regularly.** Run `./scripts/status.sh` to see where every issue stands. Run with `--write` to update `issues/STATUS.md` and commit it.
- **Token discipline.** Under 100k tokens per session. Clear context between tasks.
- **QA feeds the board.** Every QA session produces at least one new issue file.
- **No doc rot.** Archive old PRDs and stale spec sections once features ship.
- **Blocked by fields must be accurate.** `/plan-issues` builds the DAG from these. A missing dependency = two issues in the same phase that conflict.
- **Deep modules.** Run `/improve-architecture` quarterly.
- **Implementation Plan quality = output quality.** Vague steps produce vague code. Specific test assertions produce specific implementations.

## issues/STATUS.md — Lifecycle Tracker

`STATUS.md` tracks every issue from creation through merge. Updated by `./scripts/status.sh --write`.

**Lifecycle states:**

| State | Trigger |
|---|---|
| 🔒 blocked | Issue has blockers not yet merged |
| ⏳ open | No blockers — ready to implement |
| 🔨 in-progress | Worktree directory exists in `../.worktrees/` |
| ✗ audit-failed | Audit log exists but contains CHANGES REQUIRED |
| ✓ audit-passed | Audit log contains [APPROVED], branch pushed |
| 👁 pr-open | Marked in merge-log.md as pr-open |
| ✅ merged | Issue file moved to `issues/done/` |
| 👤 manual | Issue type is Human-in-loop |

**How to use:**

```bash
# View live status in terminal (fast, no file writes)
./scripts/status.sh

# Update STATUS.md and commit (use after each phase)
./scripts/status.sh --write
```

The terminal view also shows an "Action needed" summary at the bottom —
what audit failures need fixing, what PRs are ready to open, and what
comes next.

## scripts/status.sh — Live Status Script

Reads the current state of every issue by checking:
- `issues/open/` and `issues/done/` (issue file locations)
- `../.worktrees/*/` (active worktree directories → in-progress)
- `../.worktrees/*.audit.log` (audit results)
- `issues/EXECUTION_PLAN.md` (phase assignments)
- `issues/merge-log.md` (PR numbers and merge records)
- Git remote branches (PR open vs merged)

No external API calls — reads only local files and git. Fast to run at any point.
